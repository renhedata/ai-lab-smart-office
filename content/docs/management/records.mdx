---
title: 需求、试点与决策记录
description: 用轻量编号、实用性评分、试点指标和决策日志保留项目全过程。
---

项目不需要一开始就建一套复杂管理系统。只要保证一个问题能追踪到试点、决策、上线变更和最终结果，GitHub Issue + 本文档站就足够起步。

```text
NEED-xxx 真实需求 → EXP-xxx 试点 → DEC-xxx 决策 → CHG-xxx 上线变更 → MET-xxx 效果复查
```

不单独维护一个手工流水号表。记录建立成 GitHub Issue 后，直接使用 Issue 编号作为后缀，例如需求 Issue `#42` 就是 `NEED-42`，关联试点 Issue `#57` 就是 `EXP-57`。这样不会因为多人并行录入而重号。

| 记录 | 何时创建 | 保留什么 | 推荐载体 |
| --- | --- | --- | --- |
| `NEED` 需求 | 出现可复现问题或明确改进机会 | 场景、频率、人群、影响、现有做法和证据 | Issue |
| `EXP` 试点 | 需求已核实，但仍有高风险假设 | 范围、基线、目标、暂停条件、数据和日期 | 主 Issue + 测试记录 |
| `DEC` 决策 | 选择、拒绝、暂缓、替代或退役方案 | 备选、依据、取舍、反对意见、回退和复核日期 | 决策 Issue + 稳定方案页 |
| `CHG` 变更 | 现场、配置或流程实际发生改变 | 影响区域、版本、验证、回滚和操作人 | Pull Request / 变更 Issue |
| `MET` 效果 | 试点结束、上线 30/90 天或定期复查 | 基线对比、工单、使用体验、维护成本和后续决定 | 验收/复盘 Issue |

## 需求卡：先记问题

```md
# NEED-___ 简短标题

- 受影响的人/区域：
- 具体场景和时间：
- 现在发生什么：
- 现有处理方式：
- 发生频率 / 耗时 / 失败 / 不适：
- 证据（现场观察、工单、统计或脱敏反馈）：
- 希望结果（不必写设备）：
- 可能影响的其他人群：
- 隐私、安全、无障碍或劳动管理风险：
- 负责人 / 当前状态 / 下次更新日：
```

## 先过硬门槛，再排优先级

任何一项不满足，暂不进入采购或真实环境自动执行：

- [ ] 有明确问题、受益人和可复核证据，不只是一个设备想法。
- [ ] 已比较“不做”、改流程/标识、简单设备和自动化方案。
- [ ] 不触犯消防、电气、网络、人身安全、个人信息和用工管理边界。
- [ ] 保留人工替代、明确回退/暂停条件，并有长期运维负责人。
- [ ] 可以以有限区域、时间和成本试点，且有试点前基线。

硬门槛通过后，每项用 `0～3` 分记录事实；评分不取代最终责任人的判断。

| 维度 | `0` 分 | `3` 分 |
| --- | --- | --- |
| 痛点强度 | 主要是喜好或展示 | 阻断任务、持续不适或存在安全影响 |
| 影响广度 | 极少出现 | 多个团队/空间高频出现 |
| 证据强度 | 只有假设 | 有多次观察、工单或基线数据 |
| 可验证收益 | 无法定义改善 | 任务、时间、舒适、能耗或故障指标可测 |
| 学习价值 | 只适用单一特例 | 能验证多个区域的关键假设 |
| 一次性成本 | 费用/施工高且难回滚 | 低成本、可借用或可丢弃原型 |
| 持续运维 | 无人会修、频繁电池/订阅/升级 | 已有负责人、备份和简单故障路径 |
| 锁定与退出 | 专有云端、数据难导出、无替代 | 本地/开放接口、配置可备份、有替换路径 |

隐私、安全和法律风险不是“扣几分”就可以被其他高分抵消；它们属于硬门槛，需要单独评审。

## 试点卡：先验证最危险的假设

```md
# EXP-___ 试点名称

- 关联需求：NEED-___
- 假设：对【人群】在【场景】做【变化】，【指标】会从 ___ 改善到 ___
- 区域 / 参与人 / 开始与结束日：
- 成本上限：
- 试点前基线：
- 每周观察指标：
- 人工替代和回退步骤：
- 立即暂停条件：安全风险 / 影响正常办公 / 高频误动作 / 隐私质疑未处理 / ___
- 数据项、查看人、保存期和删除日：
- 支持人 / 验收人 / 评审会日期：
- 结论：推广 / 修改再试 / 停止
```

建议先在桌面或非生产环境验证设备/协议；D 会议室作为首选候选，经 `NEED` 核实和 `DEC` 批准后再做一个完整闭环。稳定后再增加一个开放办公子区和不同朝向窗帘。这比同时在四个区域上线更容易定位失败原因。

## 一次试点至少看六类结果

| 类别 | 可选指标 |
| --- | --- |
| 实用 | 任务成功率、准备/收尾时间、主动使用率 |
| 可靠 | 误动作、离线次数、延迟、人工覆盖率、恢复时间 |
| 体验 | 舒适度、噪声、等待、是否知道怎样手动控制 |
| 运维 | 工单数、维护工时、电池/耗材、备份与升级难度 |
| 价值 | 采购、安装、订阅、能源成本和每次有效使用成本 |
| 信任与公平 | 员工能否说清采什么数据、隐私投诉、不同岗位是否出现明显差异 |

不要只看平均满意度或能耗。系统日志、工单、观察、简短访谈和匿名反馈可以相互验证。

## 决策记录：改变结论时不覆盖历史

```md
# DEC-___ 决策标题

- 日期 / 状态：Proposed / Accepted / Rejected / Superseded / Retired
- 决策负责人：
- 关联需求、试点和证据：
- 考虑过的选项（包括“不做”）：
- 成本、运维、隐私、安全、无障碍和供应商锁定取舍：
- 最终决定与理由：
- 反对意见或未解疑虑：
- 成功指标 / 回退条件 / 复核日期：
- 被哪个新决策替代（如适用）：
```

已接受或已拒绝的决策记录不应直接重写。结论变化时，建立新记录并将旧记录标为 `Superseded` 或 `Retired`，保留当时的证据和理由。

## 固定运营节奏

| 节奏 | 只做什么 | 输出 |
| --- | --- | --- |
| 每周 30 分钟 | 对新反馈分流，更新阻塞和下一步 | 负责人、状态、下次日期 |
| 试点每周 | 看误动作、使用体验、工单和维护负担 | 调参、继续、暂停或终止 |
| 每月 45 分钟 | 公开展示听到的问题、数据、决定和下月试点 | 月度共创回顾 |
| 上线 30/90 天 | 复查实际收益和持续成本 | 保留、继续优化或退役决策 |
