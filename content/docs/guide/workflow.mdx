## 五个对象

| 对象 | 用途 | 示例 |
| --- | --- | --- |
| 公司内部快速反馈 | 让不使用 GitHub 的员工也能提问题，由协调人脱敏代录 | 会议室太闷、灯误关、空调难用 |
| Markdown 文档 | 稳定的方案、规范、记录 | 网络方案、设备台账、运维手册 |
| GitHub Discussions | 开放式问题、方案提议、经验交流与共识形成 | 讨论传感器协议、征集试点反馈 |
| GitHub Issue | 一项待决、待做或待验收的工作 | 采购会议室传感器、修复 AP 覆盖盲区 |
| Pull Request | 对文档/配置的可审核变更 | 合并新的 VLAN 规划与交换机配置 |

无论反馈来自 GitHub、内部表单、访谈还是现场会议，项目协调人都应给出 `NEED` 编号和当前状态。GitHub Discussions 用于形成共识；具体工作建立 Issue；重要选择建立 `DEC` 决策记录，再通过 Pull Request 同步稳定方案、图纸或台账。见[需求、试点与决策记录](/docs/management/records/)。

## 推荐状态

`新提交 → 待核实 → 已验证需求 → 待设计 → 试点中 → 已推广 / 继续迭代 / 暂缓 / 拒绝 / 已退役`

以下情况必须新建 Issue：新增费用、改变设备型号、变更布线/电力、自动化规则变更、新增数据采集或供应商、现场发现问题、验收不通过。已拒绝或已退役的记录保留，不用删除代替结论。

## 回应节奏

- 2 个工作日内确认收到并给出编号。
- 每周一次 30 分钟分流，合并重复问题并指定核实人。
- 10 个工作日内至少更新一次状态、理由和下一步。
- 每月公开一次“听到什么—验证了什么—做了什么—下次何时复查”。

## GitHub Projects 字段

在组织级 Project 建立以下字段：

- `状态`：新提交、待核实、已验证需求、待设计、试点中、已推广、继续迭代、暂缓、拒绝、已退役
- `区域`：前台、办公区、会议室、机房/弱电间、公共区
- `系统`：网络、照明、环境、安防、影音、自动化、文档
- `记录类型`：`NEED`、`EXP`、`DEC`、`CHG`、`MET`
- `预算` 与 `实际金额`
- `下次更新日`、`计划完成日`、`负责人`、`供应商类别/代号`（合同和联系人留在内部系统）

GitHub Projects 可把相同项目数据切换为表格、看板和路线图，因此无需复制多份进度表。[GitHub 官方说明](https://docs.github.com/en/issues/planning-and-tracking-with-projects)

## 提交约定

- 一个 Pull Request 聚焦一个可描述的变更。
- 公开提交只写脱敏事实、设备类别、Issue 编号和内部证据编号；原始现场照片、精确资产/网络信息、合同和日志留在内部系统。
- 合并前至少由一位了解现场的人复核。
- 不提交密码、密钥、门禁凭证和个人敏感信息。
