# ADR-001: 部署环境监听型上下文感知 AI 助理

- 日期: 2026-08-03
- 状态: 提议
- 关联 Issue: 待建

## 背景与目标

**当前问题：** 
传统的智能语音交互采用“一问一答”的无状态模式。在真实的办公室商业洽谈中，需即时查阅数据时，手动唤醒并复述背景会严重打断对话心流，无法体现智能办公的压迫感与专业度。

**约束：**
1. 隐私安全：绝不允许将客户的商业机密对话完整音频流式上传至云端。
2. 架构规范：新增硬件必须符合 AI 实验室的 VLAN 划分与策略路由基线。
3. 交互时延：从触发到大屏多模态呈现，必须控制在极短时间内。

**目标：**
构建“沉默的专家”系统。AI 在本地实时转录对话并维持短期的滚动上下文记忆。仅在接收到特定触发短语时，锁定记忆池并结合云端大模型 (LLM) 执行检索，最终输出多模态响应。

## 备选方案

1. **方案 A: 全云端流式处理**
   - 优点：开发成本低。
   - 缺点：致命的商业隐私泄露风险；违反局域网安全准则。

2. **方案 B: 边缘端记忆池 + 云端按需推理**
   - 优点：利用本地算力运行 ASR（自动语音识别）实现本地文本转录，绝对保障物理级隐私；仅唤醒后上报脱敏文本，响应高效。
   - 缺点：需额外部署边缘算力节点，系统事件驱动架构较复杂。

**最终选择及原因：**
强烈建议选择 **方案 B**。对于 To-B 场景，数据隐私是不容谈判的底线。边缘端截留原始音频的架构是唯一合规的打法。

## 部署边界与网络策略

根据团队网络与布局基线，确立以下实施边界：

- **物理坐标**：试点设于 D 区的 **D会议室**。
- **设备台账命名**：边缘算力节点与麦克风阵列统一定名为 `D-MEET-AI-01`[cite: 3]。
- **网络网段**：该节点作为物联网边缘设备，计划接入 **IoT 网段 (VLAN 20, `192.168.20.0/23`)**。
- **⚠️ 路由策略 (待网络负责人确认)**：由于该节点需调用外部云端大模型 API，需网络负责人评估：其出站 443 端口流量是直接放行，还是必须经由 Arch Linux 旁路由 (`192.168.10.62`) 的 Hysteria TProxy 进行策略转发以保持对称回程[cite: 1]。

## 容灾回退与验收标准

根据 D会议室灯光试点的协同要求，本系统不以“能动”为最终目的，必须满足以下异常处理与验收标准：

| 测试场景 | 预期动作 | 必须避免 |
| --- | --- | --- |
| **断网 / 旁路由宕机** | 系统立刻进行本地语音播报（“网络连接异常”），大屏弹出故障提示图。 | 无任何响应，导致客户认为是设备死机[cite: 2]。 |
| **远场麦克风故障** | 允许用户通过扫描桌面二维码，在手机强制门户中手动输入文本，直接发起 API 请求。 | 失去唯一交互入口，整个演示流程瘫痪[cite: 2]。 |
| **大模型 API 超时** | 大模型响应超过 5 秒，系统自动降级，输出预设的安抚性语音及占位图表。 | 屏幕长时间卡死等待。 |
