本页用 **D会议室智能灯光 + 智能窗帘试点** 演示一项工作如何在项目负责人、现场、网络、自动化、采购和验收人员之间流转。重点不是某个品牌或参数，而是让每个结论都有负责人、依据、状态和可复核证据。

<Callout type="warn" title="这是协作示例，不是已冻结方案">

下文的 Issue 编号、照度阈值、灯光亮度、时间和设备型号均为示例。真正实施时，必须用现场数据替换，并在关联 Issue 中完成审批。

</Callout>

## 案例目标

| 项目 | 示例内容 |
| --- | --- |
| 区域 | D会议室 |
| 试点范围 | 两组灯光、一个存在与照度传感器、一组西侧窗帘、一个墙面场景面板 |
| 正常会议 | 有人且照度不足时进入会议照明；无人达到等待时间后关闭 |
| 演示场景 | 用户按“演示”后关闭窗帘，降低前区灯光并关闭屏幕侧灯光 |
| 人工优先 | 墙面开关和窗帘开/停/关始终可用；人工操作后暂停自动规则 |
| 故障回退 | 自动化平台或网络不可用时，灯光和窗帘仍可现场操作 |
| 完成标志 | 正常、人工覆盖、传感器异常、网络中断和平台停机测试全部通过并留有证据 |

首轮不包含空调、新风、门禁、消防和会议终端控制；这些系统只记录接口需求，不在本案例中联动。

## 参与者和职责

| 角色 | 本案例中的责任 | 主要产出 |
| --- | --- | --- |
| 项目负责人 | 明确业务目标、预算边界和最终优先级 | 主 Issue、状态推进、范围批准 |
| 现场负责人 / 电气人员 | 核对回路、开关、窗户、电机供电和安装条件 | 勘查记录、照片、接线与回退说明 |
| 网络负责人 | 确认控制主机、网关和设备的网络边界 | VLAN、地址、访问规则和连通性结果 |
| 自动化负责人 | 编写场景规则、异常处理和日志 | 配置变更、Pull Request、联调记录 |
| 采购负责人 | 比价并核对协议、供电、保修和交期 | 报价、采购 Issue、设备台账 |
| 验收负责人 | 按冻结标准独立复测，不以“能动”代替验收 | 测试记录、问题清单、验收结论 |

同一个人可以承担多个角色，但“实施”和“最终验收”最好由不同的人完成。

## 一项工作如何流转

<Steps>

<Step>

### 建立一个主 Issue

项目负责人先建立主 Issue，把目标、边界和成功标准写清楚。此时状态为 `待评审`，不采购、不施工。

```md title="Issue #42（示例）"
标题：[D会议室] 智能灯光与窗帘试点

- 状态：待评审
- 区域：D会议室
- 系统：照明 / 窗帘 / 自动化
- 负责人：项目负责人
- 预算上限：待评审
- 计划完成日：待评审

## 目标
- 有人且照度不足时自动进入会议照明。
- 按“演示”后关闭窗帘并调整灯光。
- 手动操作优先，平台故障时仍可本地控制。

## 完成条件
- 现场勘查、方案决策、设备台账和验收记录齐全。
- 正常、异常、断网、平台停机和人工覆盖测试通过。
```

需求变化、增加费用或扩大房间范围，都继续记录在这个 Issue；不要在聊天中口头改变范围。

</Step>

<Step>

### 现场核对并回报阻塞项

现场负责人逐项核对，不确定的内容写成阻塞项，不能用“应该可以”代替测量。

- 灯光有几个实际回路，负载和驱动协议是什么？
- 墙面开关是否有零线、控制线和检修空间？
- 西侧窗帘的宽度、轨道、电源和电机更换空间是否满足？
- 传感器安装高度、视野和静坐覆盖是否合适？
- 平台停机后，墙面开关是否能绕过平台直接控制？

```md title="现场回报（示例）"
- 已确认：会议室现有两组照明回路，墙面开关可保留。
- 已确认：西侧一组窗帘，现场具备检修位置。
- 待确认：吊顶内尚未确认窗帘电源路径。
- 阻塞：未确认电源前，不下单窗帘电机。
- 证据：现场照片编号 D-MEET-SURVEY-01～06、回路测试视频 01。
```

项目负责人把状态保持在 `待评审`，直到阻塞项有结论。

</Step>

<Step>

### 评审方案并确认选择

团队比较“全无线改造”和“有线控制骨干 + 无线传感器”两种方案，并在主 Issue 中说明选择、影响和回滚方式。

本示例采用以下结论：

1. 固定灯光回路和窗帘电机使用有线执行器，墙面本地控制不依赖 Home Assistant。
2. 存在与照度传感器可以使用 Zigbee，但传感器离线不能直接触发关灯。
3. 窗帘控制器必须具备开/关互锁；人工开、停、关的优先级高于自动遮阳和演示场景。
4. 自动化平台只负责编排和记录，不能成为灯光、窗帘的唯一控制路径。

项目负责人批准选择和预算后，把主 Issue 状态改为 `已批准`，并与方案修改一同通过 Pull Request 评审和合并。

</Step>

<Step>

### 拆分任务并行推进

主 Issue 保留整体范围，各负责人建立或关联可独立验收的子任务。

| 子任务 | 负责人 | 前置条件 | 交付物 |
| --- | --- | --- | --- |
| `S-01` 回路、窗户与供电复测 | 现场负责人 | 无 | 测量表、照片、阻塞项 |
| `P-01` 设备比价与兼容性核对 | 采购负责人 | `S-01` | 报价、选型理由、交期 |
| `N-01` 网关与平台连通 | 网络负责人 | 设备接口已确定 | 地址、访问规则、连通测试 |
| `L-01` 灯光和窗帘安装 | 电气人员 | `P-01` 到货 | 标签、接线图、本地控制测试 |
| `A-01` 场景与异常规则 | 自动化负责人 | `N-01`、`L-01` | 配置、日志、Pull Request |
| `T-01` 联调与验收 | 验收负责人 | `A-01` | 测试证据、问题和结论 |

主 Issue 进入 `执行中`。每个子任务只汇报自己的事实；跨任务阻塞回到主 Issue 统一处理。

</Step>

<Step>

### 实施、联调并提交可审核变更

安装完成后，先证明本地控制可用，再接入平台。自动化负责人根据[自动化场景](/docs/implementation/automation/)实现规则，并通过 Pull Request 提交可审核的文档或配置模板。

| 条件 | 预期动作 | 必须避免 |
| --- | --- | --- |
| 有人且照度低于试运行阈值 | 进入会议照明 | 仅因预约开始就点亮空房间 |
| 用户按“演示” | 关闭窗帘，降低前区灯光，关闭屏幕侧灯光 | 场景结束后无法恢复 |
| 用户手动开灯或操作窗帘 | 暂停相关自动规则，直到会议结束或区域无人 | 自动化立即抢回控制权 |
| 存在传感器离线 | 保持保守状态并告警 | 直接判断无人并关灯 |
| Home Assistant 停机 | 墙面开关和窗帘开/停/关仍可用 | 灯光或窗帘失去控制 |
| 窗帘执行开、停、关 | 开/关输出互锁并保留保护间隔 | 正反转同时输出 |

提交中不得包含密码、令牌、私钥或设备密钥。设备标识、版本、变更原因、回滚步骤和关联 Issue 要写入 Pull Request。

自动执行分两段开放：先用 **3～5 天建议模式**只记录“本来会执行什么”，确认触发条件没有明显错误；再启用自动执行并进行**不少于两周试运行**。误关灯、规则抢回控制、窗帘定位漂移等问题都要回到 Issue，修复经 Pull Request 评审后再复测。

</Step>

<Step>

### 独立验收并关闭工作

验收负责人使用已批准的成功标准复测，而不是由实施人员口头宣布完成。

| 测试 | 示例条件 | 通过标准 | 证据 |
| --- | --- | --- | --- |
| 正常会议 | 有人、照度低于阈值 | 灯光按设定进入会议状态 | 时间、照度、动作日志、视频 |
| 光线充足 | 有人、照度高于阈值 | 不重复开灯 | 照度与状态日志 |
| 演示场景 | 按墙面“演示” | 窗帘和灯光一次到位，可主动退出 | 视频、场景日志 |
| 人工覆盖 | 手动调整灯光和窗帘 | 自动规则在覆盖期内不抢回 | 操作与恢复时间 |
| 静坐测试 | 连续办公半天 | 不因静坐误关灯 | 观察记录 |
| 传感器异常 | 模拟传感器离线 | 告警且不直接关灯 | 告警截图、状态日志 |
| 断网 / 平台停机 | 中断网络并停止平台 | 本地灯光和窗帘仍可操作 | 现场视频 |
| 电机保护 | 连续执行开、停、关 | 无同时输出，停止与恢复正常 | 控制器日志、视频 |

发现问题时，主 Issue 回到 `执行中`，记录失败条件、负责人和复测日期；通过后再进入 `待验收`。只有以下内容全部完成，项目负责人才能改为 `已完成`：

- 验收记录已关联主 Issue，失败项均已关闭或明确列为遗留项。
- [采购与设备台账](/docs/management/procurement/)已补充资产、型号、位置和保修信息。
- 场景规则、回滚方法和平台停机操作已写入文档。
- 配置已备份且恢复步骤已复核。
- 文档、现场标签、实际接线和设备台账保持一致。

</Step>

</Steps>

## 协作回报长什么样

下面是同一个主 Issue 中不同角色的示例回报。每条回报都包含事实、证据和下一步，不只写“已处理”。

<Tabs items={["现场回报", "自动化回报", "验收结论"]}>

<Tab value="现场回报">

**现场负责人**

- 完成两组照明回路和一组窗帘的标签核对。
- 墙面开关脱离平台时可以控制灯光；窗帘开/停/关测试正常。
- 窗帘电源路径已确认，接线照片见 `D-MEET-INSTALL-01～04`。
- 下一步：网络负责人确认网关地址后交给自动化负责人联调。

</Tab>

<Tab value="自动化回报">

**自动化负责人**

- 已实现会议、演示、人工覆盖和传感器离线四类规则。
- 人工操作后，相关自动规则暂停到会议结束或区域确认无人。
- 已完成 Home Assistant 停机测试，本地控制不受影响。
- 配置变更和回滚说明见关联 Pull Request；下一步交验收负责人执行 `T-01`。

</Tab>

<Tab value="验收结论">

**验收负责人**

- 8 项测试中 7 项通过。
- “传感器离线”测试未产生告警，主 Issue 已退回 `执行中`。
- 自动化负责人补充告警并提交修复后，需要单独复测该项；其他通过项保留原证据。
- 复测通过前不签署最终验收结论。

</Tab>

</Tabs>

## 状态推进规则

| 状态 | 谁推进 | 进入下一状态前必须具备 |
| --- | --- | --- |
| 想法 | 任意成员 | 问题、区域和期望结果可被理解 |
| 待评审 | 项目负责人 | 现场边界、备选方案、预算影响和验收标准 |
| 已批准 | 项目负责人 | 负责人、预算和计划日期；如涉及重要取舍，Issue 已写清依据、影响和最终选择 |
| 执行中 | 各任务负责人 | 持续回报事实、阻塞、证据和下一步 |
| 待验收 | 实施负责人申请 | 安装、配置、文档、台账和自测完成 |
| 已完成 | 验收负责人确认 | 测试通过、遗留项明确、备份和移交完成 |

<Callout title="最小协作闭环">

一个主 Issue 管范围、状态和重要选择；子任务管具体负责人；Pull Request 审核稳定结论；台账保存已购设备；验收记录证明结果。聊天只用于沟通，不作为唯一证据。

</Callout>
