协作示例：智能灯光与窗帘

以 D会议室试点为例，演示从需求、勘查和决策到实施、联调与验收的完整协作过程。

本页用 D会议室智能灯光 + 智能窗帘试点 演示一项工作如何在项目负责人、现场、网络、自动化、采购和验收人员之间流转。重点不是某个品牌或参数，而是让每个结论都有负责人、依据、状态和可复核证据。

这是协作示例，不是已冻结方案

下文的 Issue 编号、照度阈值、灯光亮度、时间和设备型号均为示例。真正实施时，必须用现场数据替换，并在关联 Issue 中完成审批。

案例目标

项目示例内容
区域D会议室
试点范围两组灯光、一个存在与照度传感器、一组西侧窗帘、一个墙面场景面板
正常会议有人且照度不足时进入会议照明；无人达到等待时间后关闭
演示场景用户按“演示”后关闭窗帘，降低前区灯光并关闭屏幕侧灯光
人工优先墙面开关和窗帘开/停/关始终可用；人工操作后暂停自动规则
故障回退自动化平台或网络不可用时，灯光和窗帘仍可现场操作
完成标志正常、人工覆盖、传感器异常、网络中断和平台停机测试全部通过并留有证据

首轮不包含空调、新风、门禁、消防和会议终端控制；这些系统只记录接口需求，不在本案例中联动。

参与者和职责

角色本案例中的责任主要产出
项目负责人明确业务目标、预算边界和最终优先级主 Issue、状态推进、范围批准
现场负责人 / 电气人员核对回路、开关、窗户、电机供电和安装条件勘查记录、照片、接线与回退说明
网络负责人确认控制主机、网关和设备的网络边界VLAN、地址、访问规则和连通性结果
自动化负责人编写场景规则、异常处理和日志配置变更、Pull Request、联调记录
采购负责人比价并核对协议、供电、保修和交期报价、采购 Issue、设备台账
验收负责人按冻结标准独立复测，不以“能动”代替验收测试记录、问题清单、验收结论

同一个人可以承担多个角色，但“实施”和“最终验收”最好由不同的人完成。

一项工作如何流转

建立一个主 Issue

项目负责人先建立主 Issue，把目标、边界和成功标准写清楚。此时状态为 待评审，不采购、不施工。

需求变化、增加费用或扩大房间范围，都继续记录在这个 Issue；不要在聊天中口头改变范围。

现场核对并回报阻塞项

现场负责人逐项核对，不确定的内容写成阻塞项，不能用“应该可以”代替测量。

  • 灯光有几个实际回路，负载和驱动协议是什么？
  • 墙面开关是否有零线、控制线和检修空间？
  • 西侧窗帘的宽度、轨道、电源和电机更换空间是否满足？
  • 传感器安装高度、视野和静坐覆盖是否合适？
  • 平台停机后，墙面开关是否能绕过平台直接控制？

项目负责人把状态保持在 待评审，直到阻塞项有结论。

评审方案并记录决策

团队比较“全无线改造”和“有线控制骨干 + 无线传感器”两种方案，并在决策记录中说明选择、影响和回滚方式。

本示例采用以下结论：

  1. 固定灯光回路和窗帘电机使用有线执行器，墙面本地控制不依赖 Home Assistant。
  2. 存在与照度传感器可以使用 Zigbee，但传感器离线不能直接触发关灯。
  3. 窗帘控制器必须具备开/关互锁；人工开、停、关的优先级高于自动遮阳和演示场景。
  4. 自动化平台只负责编排和记录，不能成为灯光、窗帘的唯一控制路径。

项目负责人批准决策和预算后，把主 Issue 状态改为 已批准。对应的 ADR 与方案修改通过 Pull Request 评审并合并，写法参考决策记录。

拆分任务并行推进

主 Issue 保留整体范围，各负责人建立或关联可独立验收的子任务。

子任务负责人前置条件交付物
S-01 回路、窗户与供电复测现场负责人无测量表、照片、阻塞项
P-01 设备比价与兼容性核对采购负责人S-01报价、选型理由、交期
N-01 网关与平台连通网络负责人设备接口已确定地址、访问规则、连通测试
L-01 灯光和窗帘安装电气人员P-01 到货标签、接线图、本地控制测试
A-01 场景与异常规则自动化负责人N-01、L-01配置、日志、Pull Request
T-01 联调与验收验收负责人A-01测试证据、问题和结论

主 Issue 进入 执行中。每个子任务只汇报自己的事实；跨任务阻塞回到主 Issue 统一处理。

实施、联调并提交可审核变更

安装完成后，先证明本地控制可用，再接入平台。自动化负责人根据自动化场景实现规则，并通过 Pull Request 提交可审核的文档或配置模板。

条件预期动作必须避免
有人且照度低于试运行阈值进入会议照明仅因预约开始就点亮空房间
用户按“演示”关闭窗帘，降低前区灯光，关闭屏幕侧灯光场景结束后无法恢复
用户手动开灯或操作窗帘暂停相关自动规则，直到会议结束或区域无人自动化立即抢回控制权
存在传感器离线保持保守状态并告警直接判断无人并关灯
Home Assistant 停机墙面开关和窗帘开/停/关仍可用灯光或窗帘失去控制
窗帘执行开、停、关开/关输出互锁并保留保护间隔正反转同时输出

提交中不得包含密码、令牌、私钥或设备密钥。设备标识、版本、变更原因、回滚步骤和关联 Issue 要写入 Pull Request。

自动执行分两段开放：先用 3～5 天建议模式只记录“本来会执行什么”，确认触发条件没有明显错误；再启用自动执行并进行不少于两周试运行。误关灯、规则抢回控制、窗帘定位漂移等问题都要回到 Issue，修复经 Pull Request 评审后再复测。

独立验收并关闭工作

验收负责人使用已批准的成功标准复测，而不是由实施人员口头宣布完成。

测试示例条件通过标准证据
正常会议有人、照度低于阈值灯光按设定进入会议状态时间、照度、动作日志、视频
光线充足有人、照度高于阈值不重复开灯照度与状态日志
演示场景按墙面“演示”窗帘和灯光一次到位，可主动退出视频、场景日志
人工覆盖手动调整灯光和窗帘自动规则在覆盖期内不抢回操作与恢复时间
静坐测试连续办公半天不因静坐误关灯观察记录
传感器异常模拟传感器离线告警且不直接关灯告警截图、状态日志
断网 / 平台停机中断网络并停止平台本地灯光和窗帘仍可操作现场视频
电机保护连续执行开、停、关无同时输出，停止与恢复正常控制器日志、视频

发现问题时，主 Issue 回到 执行中，记录失败条件、负责人和复测日期；通过后再进入 待验收。只有以下内容全部完成，项目负责人才能改为 已完成：

  • 验收记录已关联主 Issue，失败项均已关闭或明确列为遗留项。
  • 采购与设备台账已补充资产、型号、位置和保修信息。
  • 场景规则、回滚方法和平台停机操作已写入文档。
  • 配置已备份且恢复步骤已复核。
  • 文档、现场标签、实际接线和设备台账保持一致。

协作回报长什么样

下面是同一个主 Issue 中不同角色的示例回报。每条回报都包含事实、证据和下一步，不只写“已处理”。

现场负责人

  • 完成两组照明回路和一组窗帘的标签核对。
  • 墙面开关脱离平台时可以控制灯光；窗帘开/停/关测试正常。
  • 窗帘电源路径已确认，接线照片见 D-MEET-INSTALL-01～04。
  • 下一步：网络负责人确认网关地址后交给自动化负责人联调。

状态推进规则

状态谁推进进入下一状态前必须具备
想法任意成员问题、区域和期望结果可被理解
待评审项目负责人现场边界、备选方案、预算影响和验收标准
已批准项目负责人决策记录、负责人、预算和计划日期
执行中各任务负责人持续回报事实、阻塞、证据和下一步
待验收实施负责人申请安装、配置、文档、台账和自测完成
已完成验收负责人确认测试通过、遗留项明确、备份和移交完成

最小协作闭环

一个主 Issue 管范围和状态；子任务管具体负责人；ADR 记录重要选择；Pull Request 审核稳定结论；台账保存已购设备；验收记录证明结果。聊天只用于沟通，不作为唯一证据。
