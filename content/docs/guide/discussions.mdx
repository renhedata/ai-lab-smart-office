项目的开放讨论统一放在 [GitHub Discussions](https://github.com/renhedata/ai-lab-smart-office/discussions)。打开页面后登录 GitHub，即可发起话题、回复他人的问题或订阅感兴趣的讨论。每篇文档末尾还设有独立的“讨论本文”评论区；它会将该页的留言归到专属 Discussion 中。

GitHub 是正式记录入口，不是唯一参与方式。没有 GitHub 账号或不希望公开姓名时，可将[参与共创](/docs/participation/)中的“30 秒反馈”发到公司指定的内部渠道，由项目协调人脱敏代录。当前内部渠道和协调人尚待指定，这是开放全员参与前的启动阻塞项。

<Callout title="从哪里进入">

文档站顶部的“参与共创”先打开参与说明，每份文档标题下方的“项目讨论”打开跨页面的项目讨论区；文档末尾的“讨论本文”仅讨论当前页面。站内不保存账号信息，身份验证完全由 GitHub 处理。

</Callout>

## 什么时候用讨论

| 情况 | 使用方式 |
| --- | --- |
| 想评论某一篇文档、补充错误或追问某段内容 | 在该文档末尾的“讨论本文”留言 |
| 普通使用问题、想听取建议、比较方向或分享跨页面经验 | 发起 GitHub Discussion；无账号时走内部快速反馈渠道 |
| 问题已核实，或已有明确范围、负责人和完成条件的工作 | 建立或关联 `NEED` / 工作 Issue |
| 已形成会影响预算、施工、网络或长期维护的选择 | 单独建立 `DEC`，关联需求与证据，并更新对应方案页面 |
| 已确认的方案、规范或验收结果 | 更新项目文档，并通过 Pull Request 审核 |

讨论用于形成共识，不代替任务跟踪。讨论中达成的结论，应同步到对应 Issue 或方案页面，避免只留在评论里。

## 发起高质量讨论

1. 先搜索已有讨论、Issue 和文档，避免重复提问。
2. 标题写清区域或系统，例如“D会议室：窗帘电机供电路径的两种方案”。
3. 说明背景、已知约束、备选方向，以及希望大家回答的问题。
4. 只附公开或脱敏材料；原始图纸、照片、日志、精确网络/资产信息和合同留在内部系统，在讨论中引用内部记录编号。
5. 讨论形成结果后，由协调人链接或新建 `NEED` Issue；若结果是重要取舍，单独建立 `DEC` 并更新对应方案页面。

## 讨论后的闭环

```text
内部快速反馈 / General Discussion
        ↓ 协调人合并、脱敏、核实
NEED Issue：状态、负责人、证据和下一步
        ↓ 需要比较重要取舍
DEC Issue：备选、决定、后果、回退和复核日
        ↓ 进入可回退试点
EXP / 工作 Issue → 验收 → 推广、迭代或停止
        ↓
Pull Request 同步稳定方案、脱敏结果和变更记录
```

## 项目组如何回应

每条新反馈在 2 个工作日内确认收到；每周分流一次；10 个工作日内至少更新一次当前状态、理由和下一步。拒绝、暂缓和退役也要留下结论，不让建议进入“已读黑洞”。
